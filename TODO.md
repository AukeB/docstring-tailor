## Bugs

The golden files under `tests/fixtures/` currently record these behaviours. When a bug is fixed, the affected golden files must be regenerated and reviewed.

1. **Code fence language tag is moved into the code block.** A fence such as ```` ```python ```` is rendered as ```` ``` ```` followed by a line containing `python` inside the block. This happens in all three styles, so the docstring's content changes, not only its formatting. Affects every fixture with a language tag, for example `sphinx/docstring_elements/code_block_multiple` and `sphinx/docstring_elements/named_paragraph_code_block`.
2. **Sphinx field tags have no closing colon.** The Sphinx renderer writes `:returns`, `:rtype` and `:raises` without the colon that reST requires, so `:returns The value…`, `:rtype list[float]` and `:raises : …` are not valid reST. Affects `sphinx/docstring_elements/structured_list`, `sphinx/docstring_elements/structured_list_malformed`, `sphinx/docstring_elements/structured_list_partial`, `sphinx/function_docstring`, and `convert/google_to_sphinx` and `convert/numpy_to_sphinx`. Likely fix: in `SphinxDocstringRenderer` (`renderer/sphinx_renderer.py`), the return tags are built as `f"{SPHINX_RENDER_RETURNS_TAG} "` and `f"{SPHINX_RENDER_RTYPE_TAG} "`; make them `f"{SPHINX_RENDER_RETURNS_TAG}: "` and `f"{SPHINX_RENDER_RTYPE_TAG}: "`. For `:raises : …`, check where an empty (not `None`) `error_type` comes from: `_render_error_field` only writes `:raises: ` without a type when `error_type is None`.
3. **NumPy to Sphinx conversion writes the wrong fields.** A NumPy `Raises` entry is written as `:param ValueError:` instead of `:raises ValueError:`, and a NumPy `Yields` entry is written as a second `:returns` field. Affects `convert/numpy_to_sphinx`.
4. **Inline literals can be split across lines.** Wrapping can break an inline literal such as ``` ``.. note::`` ``` onto two lines, which changes how it renders. Affects `sphinx/function_docstring`. Possible fix, without writing a custom wrapper: `textwrap` only breaks at spaces (and hyphens, see bug 6), so before wrapping, replace the spaces inside each inline literal with a placeholder character that is not whitespace, such as `""` from the Unicode private use area, for example with `re.sub(r"``[^`]+``", lambda match: match.group(0).replace(" ", PLACEHOLDER), text)`. After wrapping, replace the placeholder with a space again. The placeholder is one character, like the space it replaces, so the line-length calculation stays correct. Tried on 15 November 2026 on the text from `sphinx/function_docstring`: without the placeholder a literal was split at several widths between 30 and 60, with it never, and every line stayed within the width. Insert the placeholder after the existing whitespace normalisation (`re.sub(r"\s+", " ", ...)`), so it only has to replace single spaces, and do it around both `textwrap.wrap` calls listed under bug 6.
5. **The space Ruff puts after `"""` before a leading quote is removed.** When a docstring's text starts with a quote, such as `"#rrggbb" plus an opacity…`, Ruff format writes `""" "#rrggbb" plus an opacity…"""`, with a space so the docstring does not open with four quotes. docstring-tailor strips leading whitespace when it renders the text, so it writes `""""#rrggbb" plus an opacity…"""` again, and the two keep undoing each other: in pre-commit hooks each reports a changed file on every run. To match Ruff, write a space after the opening `"""` when the text starts with `"`. Likewise, keep the space before the closing `"""` when the text ends with `"`: without it the file no longer parses (Ruff keeps that space; check that docstring-tailor does not strip it). Found in mcp-musescore (0.4.1), in `src/tools/formatting.py` and `src/utils/lilypond_converter.py`. Still happens with Ruff 0.17.5 (checked 15 November 2026).
6. **Hyphenated words are split at the hyphen, and a second run turns the split into a space.** `textwrap.wrap` breaks after hyphens by default (`break_on_hyphens=True`), so when a line break falls inside a word such as `human-readable`, the output has `human-` at the end of one line and `readable` at the start of the next. When that output is formatted again, the parser joins the two lines with a space, so the word permanently becomes `human- readable`. Reproduced on 15 November 2026: `presentation/examples/example_module.py` formatted at line length 48 splits the word, and formatting that result at 120 gives `human- readable`. This changes the text, not only its layout, and breaks the promise that the result does not depend on the starting line length.

   The same happens to **words that are longer than the available width**, such as URLs: `textwrap.wrap` also cuts those (`break_long_words=True` by default). Reproduced on 15 November 2026: a docstring containing `https://example.com/a/very/long/path/to/the/documentation/page`, formatted at line length 40, splits the URL after `long/`, and formatting that result at 120 gives `https://example.com/a/very/long/ path/to/…`, a broken link.

   Fix, checked with `textwrap` directly: pass `break_on_hyphens=False` and `break_long_words=False` to both `textwrap.wrap` calls, in `utils/utils_formatting.py` (paragraph wrapping) and `renderer/base_renderer.py` (the summary line). A hyphenated word then moves to the next line as a whole, and a word longer than the width stays whole on its own line, even if that line is longer than the limit. Ruff accepts such lines as well: it does not split long strings or URLs either. No custom wrapper is needed. About 11 fixture files end a line with a hyphen, for example `google/readme_examples/readme_examples.py` (`Google-` / `style`), so the golden files must be regenerated and reviewed. Also add a fixture with a long URL.
